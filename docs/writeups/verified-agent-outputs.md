# Detecting false successes in data-science agents

A chart can look convincing even when it answers a different question. In the parity study,
one request asked for sales by region on a table with neither a region field nor sales data.
The original agent charted monthly charges by contract and returned the figure. In this
comparison, a returned output without an error counted as reported success. The checker
graded the figure as incorrect. [Parity task details](../results/week7-parity.md)

## Two checks answer different questions

DataQuorum's runtime checks are available when an analyst runs an agent. They can reject an
empty table, detect an unexpected loss of rows, or check that a numerical claim appears in
the computed EDA table. The runtime can retry after blocking validation, mark a result for review
when a warning remains, or stop early when the input cannot support the request. The final
status comes from this process, and the result includes the supporting evidence.

The evaluation checker has an advantage that the runtime does not. For each benchmark
task there is a known answer or an explicit trusted property. The checker compares the
result against that answer independently of the status. A *false success* is a result
that reported success and failed this independent test. The two layers can disagree,
so collecting only the runtime pass rate would miss precisely these cases.

## What the comparison measured

The original project and DataQuorum ran the same 55 inputs and requests with the same model,
reasoning setting, and two-retry budget. DataQuorum produced 55 correct answers and zero
false successes. The original produced 47 correct answers and seven false successes.
Eight tasks were correct only for DataQuorum. No task was correct only for the original.
The exact paired McNemar test gave p = 0.0078. [Results and caveats](../results/week7-parity.md)

The benchmark was written alongside DataQuorum, and both systems were run once per task.
These results characterize the tested requests. They do not estimate the false-success
rate on independent or repeated workloads. The confidence interval for zero false
successes still extends to about 7% in this sample.

## A failure report can point to the grader

The Week 9 checker discarded valid feature names generated by a scikit-learn
`ColumnTransformer`. It treated names such as `num__age` as missing, which flagged five
false successes. Regrading the same 31 saved outputs after fixing the checker turned
all five flags into passes. The runs themselves had not changed.
[Week 9 checker diagnosis](../results/week9-new-agents.md)

The Week 14 offline controls separated this kind of grader error from an engine failure.
One scripted EDA response made a claim absent from the summary table. Grounding caught
it and marked the result for review. With the grounding check disabled, the same response
received success and the independent grader flagged it. The scripts show that the check
can catch this failure. The paired live study is still pending.
[Week 14 controls and planned protocol](../results/week14-study.md)
